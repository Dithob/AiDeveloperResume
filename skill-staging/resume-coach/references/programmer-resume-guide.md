# Programmer Resume Guide

Use this guide for Chinese programmer resumes and software-engineering resumes influenced by the local Chinese recruiting style.

## Core philosophy

- A resume is the first screening surface and should guide later interviews.
- A strong resume is accumulated and iterated over time, not packaged in one sitting.
- The resume should make the target direction obvious and put the candidate's strongest role-relevant proof early.
- Prefer truth, specificity, and evidence over decorative wording.

## File and delivery

- Check the JD for required file naming.
- If there is no special rule, recommend: `target-role + name + application-type.pdf`, for example `Java后端开发-张三-实习生.pdf`.
- Recommend PDF for submission because Word can render unpredictably. Keep Word/DOCX or online links only as optional backups.
- Avoid special characters, meaningless numbers, and vague file names.

## Recommended structure

Required for most programmer resumes:

- Personal information
- Education
- Professional skills
- Project experience

Optional when strong and relevant:

- Work or internship experience
- Awards
- Research
- Campus experience
- Publications or patents
- Personal strengths
- Portfolio, blog, GitHub, product links

For campus recruiting, one page is usually ideal, but this is a priority rule rather than a hard rule. If the candidate has enough strong evidence, more than one page is acceptable. Put the strongest advantages and highest-value projects on page one.

Suggested section weights for early-career programmer resumes:

- Personal information: 5-10%
- Education: 10-15%
- Professional skills: 20-30%
- Projects, work, research, or campus experience: 30-50%
- Other content: 0-20%

## Personal information

Include:

- Name
- Target role
- Status such as student year or years of experience
- Phone, email, and other requested contact method
- Location if useful
- Photo only when locally appropriate or requested
- Portfolio/blog/GitHub/product links when they add credibility

Avoid:

- Overlong personal details
- Expected salary unless explicitly useful
- Irrelevant hobbies
- Long, hard-to-type links

## Education

Include school, major, degree or grade, dates, and relevant credentials.

Only include ranking when it is advantageous, usually top 20% or better. For computer-science candidates, do not waste space listing basic courses unless they are unusually strong or relevant. For non-CS candidates, include relevant high-scoring courses when they help prove role fit.

Never suggest fabricating education.

## Professional skills

Do not write a long noun pile of technologies. Split skills into concise bullets by category or domain.

Each skill line should ideally show:

- Technology or concept
- Depth or scope
- Concrete capability or usage

Prefer:

- `熟悉 Java 集合、反射、动态代理等机制，能使用 Stream API 完成数据处理。`
- `熟悉 Redis 缓存设计，能结合过期策略、热点数据和缓存一致性处理读多写少场景。`

Avoid:

- `熟悉 Java、Linux、MySQL、Redis、Kafka、RabbitMQ、Vue...`
- Skills unrelated to the target role taking prime space
- Technologies listed only because they are trendy

Order skills by JD relevance and candidate strength. Put weak or merely understood technologies later.

## Work and internship experience

Include company, role, dates, product/system context, responsibilities, technologies, and results.

Emphasize:

- Ownership: responsible for, led, designed, maintained, shipped
- Product or data scale when verifiable
- Concrete technology and method
- Business/user/engineering value
- Monitoring, incident handling, deployment, and operations when relevant

Avoid focusing on what the candidate learned. Recruiters care more about what the candidate did and what value it created.

## Project experience

This is the core for many students and junior engineers.

Include:

- Project name
- Dates
- Brief project introduction
- Tech stack or architecture
- Personal responsibilities and highlights
- Links, demos, screenshots, docs, or GitHub when credible

Keep the project introduction short. The space should mostly describe the candidate's contribution, the problem, the technical choice, and the result.

Use separate bullets. Each bullet should be concrete enough that an interviewer can ask follow-up questions.

Preferred formula:

`在 [场景/约束] 下，使用 [技术/方案]，解决/优化 [问题]，达到了 [效果/收益]。`

Project bullets should show one or more of:

- Architecture design or tradeoff decisions
- Technical depth beyond CRUD
- Performance, stability, cost, or efficiency gains
- Deployment and real user usage
- Debugging or incident resolution
- AI application, RAG, MCP, Agent, or AI coding workflow when truly practiced
- Product thinking, data analysis, or operations

## Awards and achievements

Sort by recognition, scope, award level, and relevance to the role. Remove weak awards if they crowd out stronger project or work evidence.

## Personal strengths

Use this section only when each claim has proof. Weak self-evaluations waste space.

Better pattern:

- `全栈交付能力强：独立上线 3 个可访问产品，覆盖需求分析、开发、部署和监控。`
- `开源意识强：维护 XX 项目，累计获得 XX stars，并处理 XX 个 issues。`

If there is no evidence, remove the section and give space to projects.

## Common problems to flag

- Missing required sections
- Unclear target role
- Excessive project introduction and too little personal contribution
- Duty lists without achievements
- Vague or casual wording
- Inconsistent date format
- Wrong capitalization of technical terms
- No project links, repo, blog, demo, or proof when the candidate claims substantial work
- Irrelevant technology stacks crowding out target-role evidence
- Inflated claims that cannot survive interview follow-up
- Keywords copied from a JD without matching experience

## AI-era software resume guidance

For 2026-era programmer resumes, AI ability can be a screening signal when the target role values it. Only include AI content backed by real practice.

Useful AI-related signals:

- AI application development with RAG, MCP, Agent frameworks, LangChain/LangChain4j, Spring AI, vector databases, embeddings, or tool calling
- AI coding workflow with concrete delivery proof, such as specs, design, tests, deployment, and review
- Product thinking and ability to take an idea to real users
- Observability, operations, and iteration after deployment
- Technical-wheel projects that show understanding of underlying mechanisms

Do not present AI-generated code percentage as value by itself. The value is controlling requirements, design, implementation, testing, deployment, and operation.

For AI-era summaries, express the target role with a credible AI angle when true, for example:

`Java 后端开发（具备 AI Agent 应用开发经验）`

## Review rubric

Use a 100-point score only when helpful:

- Target-role clarity: 15
- Section completeness and priority: 15
- Technical depth and specificity: 20
- Project/work impact and evidence: 25
- JD match and keyword coverage: 15
- Formatting, naming, consistency, and professionalism: 10

Always explain the score with actionable fixes.
